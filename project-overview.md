# Build DocMind — Local AI PDF RAG Application

## 1. Project Overview

Build a production-quality demo application called **DocMind**.

DocMind is an AI-powered document Q&A application where users can:

1. Upload one or more PDF documents.
2. Process and index the documents using a RAG pipeline.
3. Ask questions about the uploaded documents.
4. Get answers generated by an LLM using only relevant document context.
5. See the source documents, page numbers, and relevant excerpts used to generate each answer.

The primary goal is to demonstrate a clean, understandable, and extensible **Retrieval-Augmented Generation (RAG)** architecture.

This is a demo project, but the codebase should follow production-quality engineering practices.

# 4. PDF Upload Flow

When the user uploads a PDF:

```text
React
   ↓
FastAPI
   ↓
Validate PDF
   ↓
Save file locally
   ↓
Extract text
   ↓
Split text into chunks
   ↓
Generate embeddings
   ↓
Store chunks + embeddings in PostgreSQL/pgvector
   ↓
Document status = READY
```

Requirements:

* Only allow PDF files.
* Validate file size.
* Generate a unique document ID.
* Store uploaded files locally.
* Never store the entire PDF inside PostgreSQL.
* Store the local file path in the database.
* Preserve page numbers during extraction.
* Each chunk must contain:

  * document_id
  * page_number
  * chunk_index
  * text
  * embedding

# 5. PDF Text Extraction

Create a dedicated document-processing module.

Use a reliable Python PDF extraction library such as:

```text
PyMuPDF
```

The extraction pipeline should preserve page boundaries.

Example:

```text
Document
 ├── Page 1
 │    ├── text
 │    └── metadata
 ├── Page 2
 │    ├── text
 │    └── metadata
 └── Page 3
      ├── text
      └── metadata
```

Do not blindly concatenate the entire document before chunking.

# 8. Vector Search

Use PostgreSQL + pgvector.

Store embeddings directly with the document chunks.

When a user asks:

```text
"What was the company's revenue in 2025?"
```

perform:

```text
Question
   ↓
Generate query embedding
   ↓
Vector similarity search
   ↓
Retrieve top K chunks
   ↓
Filter/rank relevant chunks
   ↓
Build context
   ↓
Send context + question to LLM
   ↓
Return answer + sources
```

Default:

```text
top_k = 5
```

Make `top_k` configurable.

# 9. RAG Prompt

The LLM must be explicitly instructed to answer using the retrieved context.

Use a system prompt conceptually similar to:

```text
You are a document question-answering assistant.

Answer the user's question using only the provided document context.

If the answer cannot be found in the provided context, clearly say that the information was not found in the uploaded documents.

Do not invent facts.

When possible, reference the document name and page number.

Context:
{context}

Question:
{question}
```

Do not allow the model to hallucinate information that isn't present in the retrieved documents.

# 15. Background Processing

PDF processing should not block the HTTP request for large files.

Implement a background processing architecture.

For the demo, use FastAPI background tasks or a simple local job mechanism.

Flow:

```text
Upload PDF
    ↓
Create document
    ↓
status = PROCESSING
    ↓
Background job
    ↓
Extract
    ↓
Chunk
    ↓
Embed
    ↓
Store vectors
    ↓
status = READY
```

If processing fails:

```text
status = FAILED
error_message = "..."
```

The frontend should poll the document status or use WebSockets/SSE if implemented.

Do not introduce Redis/Celery unless actually necessary for the demo.

Keep the architecture simple.

# 25. Important RAG Quality Requirements

Do not implement a naive:

```text
PDF → entire text → LLM
```

pipeline.

The project must actually demonstrate RAG:

```text
PDF
 ↓
Chunks
 ↓
Embeddings
 ↓
Vector DB
 ↓
Semantic Retrieval
 ↓
Relevant Context
 ↓
LLM
```

The LLM should never receive the entire document by default.

The answer should be based on retrieved chunks.

Return source metadata along with every answer.
